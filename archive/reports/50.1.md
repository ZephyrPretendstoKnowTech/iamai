# Prompt 50.1 — The plan is derived, never stored

Six items. The first is the root cause of two of the others and of three
"verified on the fixture, absent on the live tenant" reports in a row: the Plan
was rendered from a persisted record that a stale build had written, so a
re-scan did not move it and a clause added three prompts ago never reached a
plan first generated before it. All four parts are green: `npm test` (all
passing), the smoke walk, `lint-mutations`, the inventory and the layout audit,
and `vite build`.

## Part 1 — The plan record stores decisions only

The persisted plan record held the whole generated plan: every step's status,
tracking, ring dates and history, re-stamped on each render and pinned by a rank
ratchet a re-scan could not lower. The record now holds **decisions only**
(`PlanDecisions`, `src/roadmap/decisions.ts`): the skips and their reasons, the
start date, the freeze, the checkpoints, and when the plan began. Steps,
statuses, populations, evidence lines, dates and the header line are regenerated
from the current snapshot, the decisions and the current code on every load,
re-scan and edit. `applySkips` applies the one decision a regeneration cannot
know; `trackExecution` derives the rest from the snapshot, as it already did.

- **Migration (item 2):** `decisionsOf` reads a record of any vintage for its
  decisions; a pre-50.1 blob is reduced to its skips on load and rewritten in the
  new shape on the next save, dropping the generated fields. A test loads a
  pre-50.1 record that claims a step is done and asserts the regenerated plan
  renders the snapshot's status, not the cached one.
- **The plan file** keeps its v2 shape: `buildPlanFile` writes the regenerated
  plan plus a `decisions` block; on load, `loadPlanInner` takes the decisions
  (or, for a pre-50.1 file, recovers them from the steps and schedule) and
  regenerates. The tenant guard still runs before the write.
- **UI-path proof (item 3):** the smoke opens the rendered emergency-access step
  and asserts the passkey clause is present, so a cached record can never again
  make a green test lie.

`mergePersisted` and `applyProgress` are unchanged, so the roadmap engine's
re-plan and regression tests still hold; only the live record and the plan file
changed.

## Part 2 — Readiness-held steps render

Once the plan is regenerated from the snapshot, the readiness-held steps that
"appeared nowhere" render as Blocked rows in the wave they would join.

- **Item 4:** a step a readiness threshold holds reads its reason in the date
  column, in the 46 shape (`when MFA readiness reaches 90% (now 40%)`), rather
  than a date it does not have; the blocker already carries the string, and the
  duplicate `after:` line is dropped so the row states one binding reason. A
  property test over **every fixture** asserts every step renders exactly one row
  or one footer line — nothing is generated, counted in the header, and then
  shown nowhere.
- **Item 5:** the demo seeds its exclusion and target group members, so coverage
  resolves each policy's scope. Without them every excluding policy read as
  not-in-place and the demo showed one step in place; it now shows five. By week
  two the admins phishing-resistant policy is enforced (its step moves into
  place), two Wave 1 policies sit in report-only, and the exclusions group
  exists. The smoke asserts the day-one and week-two Plans differ and the header's
  in-place count rises; the property test asserts the tracking deltas.

## Part 3 — The dependency rule narrows before it fires

Housekeeping flagged `Core - Block - Legacy authentication` and `Core - Block -
Device code flow` for excluding none of the sign-in dependencies, though both are
narrowed by a client-app or authentication-flow condition and never touch a
registration or enrolment sign-in. The block-dependency rule now fires only on a
block over all resources whose scope is **not** already narrowed by a client-app,
auth-flow, platform, device-filter or location condition. Client-app types are
the exception: the default `["all"]` narrows nothing, so only a subset without
`"all"` counts. Tests cover each of the five conditions, the `["all"]`
non-narrowing, a genuinely broad block that still fires, and the two demo
policies.

## Part 4 — Sign-in, entry, and a clause

- **Item 7:** `initialize()` does not load the authority metadata; `loginRedirect`
  fetches it lazily, so on a cold page the first click stalled and looked inert
  until the second. `signIn` now awaits `authReady` — initialise, the redirect
  handling, and a warmed fetch of the metadata — and the button carries a spinner
  while warming but stays clickable, so a click made during the warm is queued
  and fires the moment it is ready. The smoke tests the real metadata fetch, and
  asserts the warming button is clickable so an early click is not lost.
  Forgetting a tenant now clears MSAL's local cache too.
- **Item 8:** `See it with sample data →` is an ordinary anchor whose href
  changes the search, so a click is a full page load into the demo with no router
  interception; the smoke asserts a click lands on the demo Plan with the banner.
- **Item 9:** gap clauses on rows are shortened, not truncated. A per-goal short
  clause (`gapClause`) is authored in coverage beside the full sentence by
  dropping the secondary clauses a session or control gap can carry; the row
  shows it as the step's `gapShort`, and `shortGap` drops those clauses rather
  than cutting mid-word into a `…persist in the…` ellipsis.

## The rendered emergency-access action, from the mock

The mock's tenant already has emergency-access accounts, so the plan does not
show `Create two break-glass accounts`; it shows the must-fix `Sort out emergency
access before anything else` (whose Do-it is the create guidance) and the
`Break-glass sign-in drill`, which is where the passkey clause renders. Both are
regenerated from the snapshot, so the clause cannot go missing behind a cached
record again.

**`Sort out emergency access before anything else`** (the emergency-access step,

**`Break-glass sign-in drill`** — the emergency-access step that carries the
passkey clause the smoke asserts (item 3):


The full `Create two break-glass accounts` create action carries the same passkey
clause in its second portal step (`src/copy/steps.ts`, unconditional since prompt
50); it renders on a tenant whose emergency accounts are missing, and the
decisions-only regeneration now guarantees it appears there rather than being
hidden behind a stale record.
