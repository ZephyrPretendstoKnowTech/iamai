## Part 1 — The content loader

- Import `docs/design/content.json` at build time. Every rendered string on Plan, a step, More,
  Today (tiles, definitions, Show), Connect, Export and How comes from it; fill `{var}` from the
  derived model, `{list:var}` as a numbered list inside `.names`, pluralise counts
  (`{n} people` → "1 person" / "3 people"), expand shared references (`{portalRoot}`,
  `{exclusionsLine}`, `{reportOnlyLine}`, `{policyDoneWhen}`, `{policyIfWrong}`,
  `{datesNew}`, `{datesChange}`, `{existingCoverage}`, `{syncRoleNote}`, `{strengthName}`).
- A line whose only list is empty is not rendered; a line whose `{n}` is 0 and that has no
  list is not rendered; a section with nothing left is not rendered (§8.7).
- Evidence lines carry a predicate in the model; render only the ones that apply.
- Tests (`content.test.ts`): every key in the file is used by some renderer, and every string
  a renderer emits maps back to a key; no rendered text contains `undefined`, `null`, `**`,
  `—` as a value, an unfilled `{brace}`, or a word from the contract's `forbidEverywhere`; the
  rendered GetIAMAI and demo steps equal the output of `docs/design/render-review.py` for the
  same values (one shared expectation file per fixture, regenerated by that script).

## Part 2 — The engine

**2.1 One population object.** `src/derive/population.ts`: for a step, `active`, `admins`,
`guests`, `enabledCovered`, `names`, once; every count and name list a step or row shows reads
it. Extend `renderedNumbers` and `agreement` to the opened step and its More.

**2.2 One readiness value per kind** (MFA with a passkey or a working method, admin
phishing-resistant, device), computed once per plan. Two rows with different "now" values for
one kind is a failing test.

**2.3 Finish date and phases.** The header's finish is the last phase's end, Cleanup included.
Phases are `Preparation`, `Phase 1`, `Phase 2`, …, `Cleanup` — numbered, never named. Delete
the wave-name table.

**2.4 Deterministic derivation.** Stable ordering by goal id before dependency resolution; the
binding blocked reason is the first unmet prerequisite in that order (§8.5). Nothing depends
on Set or Map iteration order. `derive.deterministic.test.ts`: derive the same snapshot twice
and after a plan-file round-trip; deep-diff to nothing.

**2.5 Recognise what exists (§8.11).** Exclusions group (assigned; excluded from ≥1 enabled or
report-only policy; members ⊆ emergency candidates, or name matches `break.?glass|exclusion`);
admins group (members hold core admin roles); trusted locations; countries location; a custom
authentication strength whose combinations equal the baseline's; every registered FIDO2
method's model and AAGUID; Entra Connect (sync present, its service principal, its sign-in
address); security defaults and per-user MFA state; partner tenants from service-provider
sign-ins. Each pre-fills its step's decision. Tests on the demo snapshot ("Core - Break glass"
excluded by "Core - Grant - Admins phishing-resistant") and GetIAMAI's ("Breakglass Exclusion"
excluded by "Core - Allow - MFA for Admins"): the group is recognised; a snapshot with none
gets the create instructions; creating an object between scans removes or shortens a step and
never adds one.

**2.6 Exclusion through the group.** Every exclusion check resolves group membership: an
account is excluded from a policy when its group is. The catalogue templates' `excludeUsers:
["{breakGlass}"]` is removed; a policy that names an emergency account as a user exclusion
fails validator `excl-01`.

**2.7 Blocker steps** list every failing check by name with its fix, numbered, from the
`checkFixes` map in the content file. An empty What to do fails the build.

**2.8 The registration gate** holds until the enrol-by date (registration window, §9); after
it, the first policy enforces on schedule and the holdouts list renders. Security defaults is
scheduled on the first enforcement day, immediately before that policy; its step and the
per-user-MFA step render only when the condition is present.

**2.9 Merged goals.** A step may implement several goals (`mergesGoals`): the download pair,
the persistence pair, the guest pair. Coverage marks all of a step's goals from its policies;
in place iff all are in place.

**2.10 Licence variants.** Where a policy's control needs a licence the tenant lacks, the step
uses the nearest held control and the licensed version goes under `Not licensed` (content
`pages.plan.footer.notLicensed*`); goals the tenant cannot hold at all go there too.

**2.11 Cleanup rows** from `content.cleanup`: alerting, the drill, naming, consolidation
(policies this plan superseded, from `existingPolicies`), not-assessed baseline policies.

## Part 3 — The portal-line translator and the baseline

**3.1 Translator.** `src/roadmap/portalLines.ts`: from a Conditional Access policy object,
produce the numbered What to do lines in the content file's shape — users and groups
(placeholders resolved to the tenant's names), resources, conditions (locations, platforms,
client apps, device filter, authentication flows, risk levels, authentication context), grant
or session control, `{reportOnlyLine}` — and the JSON and PowerShell equivalents. Ids resolve to
names everywhere (roles, apps, strengths, locations). A policy with neither grant nor session
control fails.

**3.2 The baseline wins.** Each goal's What to do is rendered from the baseline's policy for
that goal, not the catalogue template. Where the content file's `whatToDo.steps` for a goal are
present they are the expected output of the translator for that baseline policy — a test
asserts equality on the pinned baseline; a mismatch is reported, never patched by hand.
Two-policy steps render Policy A and Policy B. The registration step renders its `fallback`
form when the trusted-network step is marked Doesn't apply.

**3.3 Placeholders and validators.** Implement onboarding §2 stages 1–4 and 6–7 for the pinned
baseline: normalise, resolve placeholders (exclusions group, admins group, travellers, service
accounts, trusted and countries locations, the custom strength, author-specific app exclusions
stripped and listed), map to goals, run the §3 validators as tests (`excl-01`, `sess-01`,
`sess-02`, `ret-01`, `str-01..03`, `loc-01..02`, `lic-01`, `app-01`, `pair-01`, `auth-01..02`,
`shape-01`, `name-01`, `dup-01`), render every step, pin. Stage 5 (lockout simulation) reuses
the replay engine against the GetIAMAI and demo fixtures. Write the report to
`docs/baselines/jhope188-conditionalaccesspolicies/<commit>.md`.

**3.4 Re-pin and diff.** Re-pin to the author's current head, and record the per-policy diff
from ceccdc2 in the report (admin sessions 1 h → 4 h among them). On each load, compare the
author's head with the pinned commit (one request, the same allow-listed origin); when it
differs, Connect renders `pages.connectNoScan.baselineUpdated` with the count and, under
`review`, one `baselineUpdatedRow` per changed policy. Taking the update re-derives the plan.

**3.5 Authentication methods layer.** Read the FIDO2, Authenticator and TAP method
configurations; the Set Up Passkeys step compares them with the baseline layer's expectations
(passkeys on for all users, attestation enforced, key restrictions Allow with the Authenticator
identifiers `de1e552d-db1d-4423-a619-566b625cdc84` and `90a3ccdf-635c-4729-a248-9b709135078f`
and every registered key, TAP on) and lists what differs.
