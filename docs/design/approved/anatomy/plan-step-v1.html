Product design reference · September 2026

Plan steps should feel simple because the engine is doing the hard work.

This pack defines the reusable UI and product behavior for IAMAI Plan steps. It preserves the baseline's policy boundaries, keeps the default surface concise, and gives the operator one clear next safe action at every step.

Core rule The engine may know everything. The default step shows only what changes the next safe action. Passed checks disappear; failures, decisions, and meaningful new evidence are promoted.
01 · Step contract

What constitutes a Plan step

A step normally maps to one baseline policy, control, or supporting function with its own security purpose, scope, rollout behavior, and verification. IAMAI should not collapse separate baseline policies just because they contribute to the same broader security outcome.

Working definition: A Plan step is the smallest operator-owned unit of work that can be understood, acted on, and verified independently while preserving the baseline's intended blast radius.

Baseline policy boundaries are preserved

Separate Conditional Access policies remain separate steps when their scopes, exclusions, report-only evidence, rollback, or enforcement can differ.

Every step has a next action

Implementation, decision, remediation, or resolution. A warning without a next action is not a complete Plan step.

1
State / next milestoneAlways visible. The row and header answer where this step is now and what happens next.
2
WhyAlways short. One or two sentences; deeper education belongs behind Learn or More.
3

04 · Decision primitive

Detected is not the same as confirmed

Any object that becomes an operator-owned safety decision should preserve provenance internally: observed, recommended, operator confirmed. The UI only exposes that distinction when it matters.

Recommended object pattern

Breakglass Exclusion
1 member · excluded from 8 of 8 relevant policies
Recommended

Rules

IAMAI may automatically detect evidence. It should not silently turn a discovered object into an authoritative future-plan mapping when the choice is security-sensitive. A confirmed choice persists across scans until it becomes invalid.

If two or more objects plausibly serve the same safety-critical role, IAMAI should not guess. That becomes a future security call-out and operator decision, not an automatic mapping.

06 · Implementation-facing model

Design the data contract before rewriting ContentStep

The UI should render a normalized Step View Model rather than accumulate policy-specific conditions. Every section is optional; the engine/content layer decides relevance.

PlanStepView {
  id
  kind: "policy" | "control" | "supporting" | "resolution"

  header: {
    title
    subtitle?
    lifecycle?: "not-deployed" | "report-only" | "ready-to-enforce" | "enforced"
    condition?: "healthy" | "review-required" | "blocked" | "needs-decision" | "baseline-conflict"
    nextMilestone?: { label, date? }
  }

  why: { text, learnUrl? }

  findings?: [
    { label, headline, detail, provenance? }
  ]

  impact?: {
    headline
    summaryLines[]
  }

  attention?: {
    severity
    title
    detail
    evidenceRefs?
  }

  action: {
    mode: "implement" | "decide" | "remediate" | "resolve" | "preserve"
    portal?
    json?
    powershell?
    selector?
    steps?
  }

  doneWhen?: string[]

  more?: {
    risks?
    rollback?
    source?
    exactScope?
    helpDesk?
    manager?
  }
}

Separate lifecycle from condition

Do not let a single status enum drive rollout stage, blocker reason, readiness, dates, and styling. A step can be Report-only + Review required.

One canonical resolved policy

Baseline policy + applied tenant mapping should produce one resolved policy object. Impact, Portal, JSON, PowerShell, verification, and exports consume the same semantics.

Observation record

Persist first/last observed state, configuration fingerprint, affected-population fingerprint, observed counts, and unresolved evidence summaries.

Decision provenance

Track detected, recommended, and operator-confirmed values internally so the UI never makes an inferred object look manually selected.

08 · Responsive / accessibility / overflow

Solve the expensive UI problems once

Long tenant objects

Group names, policy names, UPNs, and role names wrap naturally. Never let a long object widen the entire step or force horizontal page scrolling.

Right rail collapse

At narrower widths the rail moves below the main content. It does not disappear and it does not squeeze instructions into an unreadable column.

State not color-only

Healthy, Review required, Blocked, and Needs decision always include text/iconography in addition to color.

Interactive controls

Tabs, selectors, More disclosures, and buttons must be keyboard reachable and maintain visible focus states. Copy actions should have accessible labels.

11 · Acceptance principles

How we know the redesign is working

At a glance

A user can scan the collapsed Plan and understand which policies are not deployed, in Report-only, ready, enforced, or held by a real issue.

On open

The first screenful explains why this matters, what IAMAI found, and what the user should do next without requiring deep IAM expertise.

On complexity

The engine may evaluate many checks, but the default step shows at most the handful that change today's action. Passed prerequisites usually disappear.

On trust

Any important conclusion can be audited in More. Observed facts, IAMAI-derived recommendations, and operator-confirmed decisions do not blur together.

On safety

A policy cannot become Ready to enforce while unresolved material evidence, unsafe prerequisites, or an unresolved baseline definition remains.

On implementation

Portal, JSON, PowerShell, impact, and exports cannot disagree because they consume one canonical resolved tenant policy.
