  • Writes a dated plan for the difference: report-only before enforced, who each change touches, what would break, and the emails to send.

Read-only. It holds no permission that can create, change or delete anything.

IAMAI limitations
  • Devices that send mail without signing in (Direct Send printers, scanners) leave no record; a legacy-authentication block can stop one the plan never listed. The step asks before that block enforces.
  • Authentication that happens outside Entra (federation, third-party MFA, on-premises apps) is recorded as a sign-in but not as what the other system enforced.
  • Anything on a longer cycle than the records (the quarterly invoice run, the yearly renewal) has left no evidence yet; keep new blocks in report-only across a full cycle.
  • Credentials saved on equipment nobody has touched in years surface the day something blocks them; a walk through the comms room beats any report.
  • A partner's own tenant enforces for their people; IAMAI sees their sign-ins here, never their controls.

What IAMAI asks for, and how to remove it

Microsoft's consent screen will list these five, in this order:

  • Read all users' basic profiles / Read directory dataPeople, groups, devices, licences, the tenant's name
  • Read your organization's policiesConditional Access policies, named locations, strengths, cross-tenant settings
  • Read audit log dataSign-in records for the last 30 days
  • Read role management data for your company's directoryWho holds which role, and which through PIM
  • Read all users' authentication methodsWhich kinds of sign-in method each account has, never the values

Remove it any time: Entra admin center → Enterprise applications → IAMAI Planner → Delete. Nothing it read leaves this browser unless you export it.
