## Part 1 — The content loader — DONE

**What changed.**

- `src/content/content.ts` — imports `docs/design/content.json` at build time
  (`with { type: 'json' }`, the established pattern) and exposes the typed
  accessor: `content`, `shared`, `steps`, `stepById`, `cleanup`, `phases`,
  `pages`. This is the single import point; the engine never composes a sentence.
- `src/content/render.ts` — the fill engine and the renderers, a faithful port
  of `docs/design/render-review.py`:
  - `fill(text, ex)` fills `{var}` from the model, renders `{list:var}` as a
    numbered `.names` list, expands the shared references (`{portalRoot}`,
    `{exclusionsLine}`, `{reportOnlyLine}`, `{policyIfWrong}`, `{changeIfWrong}`,
    `{datesNew}`, `{datesChange}`, `{portalOpen}`, `{existingCoverage}`,
    `{syncRoleNote}`, signature), and marks filled values.
  - A line whose only list is empty is not rendered; a line whose `{n}` is 0 and
    has no list is not rendered; evidence lines carry a predicate and render only
    when it applies (§8.7). Python truthiness is reproduced exactly (an empty
    list is falsy) via a `truthy()` helper — the one place a naive JS port would
    have rendered a "none" line the review page suppresses.
  - `renderStep`, `renderCleanup`, `renderPages`, `reviewBody` reproduce every
    step, cleanup entry and page the script renders.
- `scripts/render-review.mjs` + `npm run render-review` — regenerate the
  checked-in expectation from the Python script (UTF-8 forced, newlines
  normalised to LF). The script `docs/design/render-review.py` is not edited.
- `docs/qa/content-review.expected.html` — the checked-in expectation, the
  script's own output. It lives under `docs/qa` (not `src`) so the host-allowlist
  walk in `src/network.test.ts` does not read its Learn links, and so the source
  fingerprint does not track it.

**What the tests assert (`src/content/content.test.ts`, 3 tests, green).**

1. `reviewBody()` equals `render-review.py`'s `<main>` body byte-for-byte
   (170,675 chars: all 38 steps, 5 cleanup entries and every page). The words the
   owner reviews and the words the app will render cannot drift; regenerating the
   expectation and reconciling is the only way to change it.
2. No rendered sentence contains any `forbidEverywhere` token (which includes
   `undefined` and `**`). The deliberate `{orange}` example-gap markers are
   `{key}`, never one of these.
3. No orphan content string: every non-structural content leaf either surfaces in
   `reviewBody()` or is one of 36 documented example-suppressed / app-only
   variants (conditional `who` lines the example does not trigger, `found.*None`
   variants, page strings the review omits that app surfaces render). A new
   content key that no renderer consumes fails this test.

`tsc --noEmit` is green. Part 1 is additive (new `src/content/`), so the full
suite gains no new failure from it.

## The blocker that shapes the rest — reported for review

The reviewer's **`page-contracts.json` version 3** and **`target-state.md`
version 2.1** describe the finished product. Three inventory-lint tests are red
from the moment those files are in the tree, before any code change:

- `the inventory matches the source it was generated from` (the source
  fingerprint tracks `page-contracts.json`, which changed);
- `rule 12: allow list — every … on a built surface is in its contract`;
- `rule 12: enforceAll — every inventory surface has a contract`.

They stay red until the surfaces are rebuilt to render exactly what contract v3
lists (Parts 4–6) and `npm run inventory` is regenerated. So **CI cannot be green
until Parts 4–6 are done**, and the prompt's "full gauntlet once, at the end" is
only reachable then. This is why Part 1 was committed but not pushed: pushing a
commit whose CI is red violates the repo's "done means green CI" rule, and the
green end-state is a whole-prompt milestone, not a Part-1 deliverable.

When the loader adds `docs/design/content.json` to the source fingerprint (needed
so a copy-only edit invalidates the inventory — `src/fingerprint.ts`
`FINGERPRINTED_FILES`), that is done in the part that first renders a surface from
the file (Part 4), not Part 1, because nothing renders from it yet.

## Parts 2–7 — reported for review with the case (not built this session)

Each is real, and each is large; none was half-built. The engineering each needs:

**Part 2 — The engine.** One consolidated `src/derive/population.ts` object read
by every count and name (today population lives in three places:
`src/roadmap/population.ts`, `src/coverage/population.ts`, `src/derive/whoLine.ts`);
one readiness value per kind computed once; finish = last phase's end with
`Cleanup`; phases numbered (`Preparation` · `Phase {n}` · `Cleanup`) with the
wave-name table deleted; deterministic derivation with a stable goal-id ordering
and `derive.deterministic.test.ts`; the recognition engine (§8.11: exclusions
group, admins group, trusted/countries locations, custom strength, FIDO2
models/AAGUIDs, Entra Connect, security-defaults/per-user-MFA, partner tenants),
each pre-filling its step's decision; exclusion resolved through the group
(remove the templates' `excludeUsers: ["{breakGlass}"]`, validator `excl-01`);
blocker steps listing failing checks from `content.checkFixes`; the registration
gate; merged goals (`mergesGoals`); licence variants; Cleanup rows. This is a
rewrite of the existing coverage/generate/scheduling engine and the goal
catalogue, with a high blast radius across the ~950 existing tests; it is the bulk
of the prompt and was not safe to part-build in the remaining session.

**Part 3 — The portal-line translator and the baseline.** `src/roadmap/portalLines.ts`
turning a Conditional Access policy object into the numbered What-to-do lines
(users/groups with placeholders resolved to tenant names, resources, conditions,
grant/session control, `{reportOnlyLine}`) plus JSON and PowerShell, ids resolved
to names; "the baseline wins" (each goal's What to do from the baseline's policy,
with `whatToDo.steps` in the file as the pinned expected output); the full
baseline-onboarding pipeline (`docs/design/baseline-onboarding.md` §2 stages 1–7)
with the ~20 §3 validators each as a test (`excl-01`, `sess-01..02`, `ret-01`,
`str-01..03`, `loc-01..02`, `lic-01`, `app-01`, `pair-01`, `auth-01..02`,
`shape-01`, `name-01`, `dup-01`); the re-pin to the author's head with the
per-policy diff from `ceccdc2`; and the authentication-methods layer. The baseline
report path when built: `docs/baselines/jhope188-conditionalaccesspolicies/<commit>.md`.
This is a second milestone of its own.

**Part 4 — The step body.** `Step.tsx` rebuilt to render section-by-section from
`src/content/render.ts` against the derived model, with `.decision` /
`.copy-box` / `Doesn't apply here` / `Scan to update the plan` / More; every
summary/change-line generator deleted (`MANAGER`, `stepContent`,
`announcementFor`, `dangers`, `plainTitleFor`, the `WHAT_CHANGES`/`EXIT`
generators). Depends on Parts 1–3.

**Part 5 — Plan page, header, sign-in.** Plan rebuilt (no assumptions strip;
two header lines; `.phase` panels; footer groups incl. `Not licensed`);
`Scan to update the plan · scanned {age}` replaces Re-scan; the Recovery card
removed (page, route `#/recovery`→`#/plan`, header link, Export row, every
`Recovery card →`); a test that `Sign in with Microsoft` reaches the sign-in call
on the first click. Depends on Part 1; the Recovery removal and the sign-in test
are the most self-contained pieces and are the natural first cut of Part 5.

**Part 6 — Vocabulary and Today.** The `forbidEverywhere`/§10 sweep over every
generator and tooltip (only meaningful once the generators are replaced by the
loader in Parts 4–5); How's `Needs`/"picker"/"relies on it" rewordings from the
file; Today's Show dropdown, tile lines, definitions and "of active" percentages
from `pages.today`.

**Part 7 — Gauntlet, walk, report.** The §12 Chrome walk of `getiamai.com/rollout`
against GetIAMAI and the demo cannot run until the app renders the new surfaces
(Parts 4–6); it is the acceptance gate for the whole prompt.
